# 一条售后场景，如何讲清楚 Agent

## 从痛点开始

用户不想研究条款，只想知道“这笔订单能不能退、退多少、下一步怎么办”。如果客服直接生成流畅回答而不查订单，就容易答错政策、误报金额，甚至把“申请已提交”说成“退款已到账”。

本地Demo将三件事分开：模型调查与选行动；程序计算与限制；客户和人工决定真实业务授权。数据全是合成的，不用这个演示冒充生产效果。

## 场景

客户：`我要退货 ord-alice-return 1件，不想要了。`

下面是一条**可能的调查路线**，不是程序硬编码的唯一顺序，也不是已执行的真实模型验收轨迹。

| 步骤 | 输入 | 谁决定 | 输出 |
|---|---|---|---|
| 接收请求 | 客户文本、服务端身份 | 程序建立run | 消息回执、run ID |
| 查询订单 | `get_order(order_id)` | 模型选工具和订单 | 本人订单项、实付分、状态、证据ID |
| 核对物流 | `get_shipment(order_id)` | 模型决定需要物流 | 签收/预计送达事实，未收到陈述不能覆盖它 |
| 查政策 | `search_policies(query)` | 模型选检索问题 | 原文、版本、适用范围 |
| 评估申请 | 订单项、数量、原因、客户陈述 | 模型请求，程序计算 | allowed options、条件、金额、版本绑定 |
| 提方案 | evaluation ID、option ID | 模型选允许选项 | 待确认方案卡，没有申请 |
| 客户确认 | proposal ID/version/hash/action_id | 客户点击，程序事务 | 唯一申请、人工工单、持久回执 |
| 人工终审 | 已确认申请和必要证据 | Staff | approved_demo/rejected，不执行支付 |
| 查结果 | `get_case()` | 模型选择查询 | 后端真实状态卡，不依据旧聊天猜测 |

每个工具结果都是下一次模型请求的Observation。即使工具和政策固定，模型仍掌握下一业务行动的选择权；这是Agent和单一路线工作流的区别。

## 程序为什么还要卡得这么严

- 模型说订单属于Alice，不算授权；后端从令牌确定身份。
- 模型写100元，不算可信金额；程序根据商品实付计算。
- 模型说客户同意，不算确认；必须精确卡片确认。
- 模型说已退款，不算成功；本工程根本没有支付执行器。
- 请求网络超时，不等于没发生；保留未知并对账，不能盲重试。

这些限制不替模型写死调查顺序，而是限定哪些行为允许真正落地。

## 怎么验证，而不是靠一句“它是真Agent”

查看源码外运行数据库里的call请求、动作和run trace：

1. 每一动作确实来自模型HTTP响应，而不是TEST策略。
2. 上一步真实Observation确实出现在下一请求。
3. 改变工具返回的证据后，模型重新作出合规决策；不要求固定文本或固定工具顺序。
4. 越权、错误金额、失效证据、重复确认都被程序挡住。
5. 浏览器、事务、模型接口Mock和真实模型评测分别标记。

当前真实模型核心场景尚未运行，因此这里只说明验证方法，不声称已经证明了具体模型的任务成功率。
